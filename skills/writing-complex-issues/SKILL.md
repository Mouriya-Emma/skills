# writing-complex-issues

交付的是能在 headless 环境仅凭完整 issue thread 执行的任务树：目标自包含；跨实现单元的权威契约在树根先定，child 内部实现细节不预钉；树里没有未决问题或等待结论的阻塞项，写作中发现的遗漏当场收口（见 decision-closure）。每份任务需要业务（谁观察到什么、为何值得做）、架构（部件与边界、防什么漂移）和已核实代码锚点。

单个 issue 的原子性、引用真实性、中文正文、结果验收和完整 GitHub 抓取入口继承 `skill://writing-issue`；图边、讨论位置与已落地记录按 `~/.claude/rules/github-issue-pr-routing.rule.md`。不要重复发布相互关联却没有共享根的平铺 issues。

## 开树前：解析操作员方向

| 输入 | 落位 | 尚未确定时 |
|---|---|---|
| 指称对象（我们的 API/CLI/系统） | 具体 repo、环境与版本锚；umbrella 说明认定依据 | 写作期定位：派 subagent 查 repo、部署与已有上下文，带证据落位；仍无法确定时直接问操作员。不编路径，不留 unknown。 |
| 原文方向 | 逐字引用并标日期；只有方向一个来源也可以，不凑假引用 | 对照实际请求，不能复述成伪造引文。 |
| 业务动机 | 有来源的 Why，不用目标复读充当动机 | 先查已有上下文；操作员独有且缺失、会改变目标或范围的事实，写作期直接问操作员并等答复。 |
| 交付约束 | 截止期转绝对日期、预算入契约；children 逐字快照继承 | 没给就不虚构。 |

按问题性质决定 parent，不按发现途径、repo 或批次机械分组。一个 child 只有一个 issue parent；跨线影响用引用。高风险第三方/跨环境假设在写作期验证，不开 gate 实现的验证 issue。

## 成树判据（发现多于一个就先问树）

树有两个入口，本方法对两者同等适用：**自顶向下**（方向 → 拆解成 children）与**自底向上**（审计 / 调查 / review 先产出 N 个发现，再组织成树）。判据：同一方向或同一次调查产出 ≥2 个相关 issue 即是树——先写树根（umbrella，或自底向上时充当树根的 audit，见 references/child-body.md）再写 children，因为契约、决策收口、共享根因、编排这些全局层**只在树根有家**，平铺发布后无处回填。

自底向上路径的失败模式（每条都让原子性合规掩盖树缺位）：

- **平铺 N 个原子 issue 各自发布**——每个 issue 单看合格，但共享根因不可见、跨 issue 的「二选一」留白原样转嫁给实现者、全局求解从未发生。
- **每个 issue「依赖关系：无」**——语义上无依赖，物理上多个 issue 同改一个文件；并行执行时互相冲突（见 references/umbrella-body.md 依赖图与编排）。
- 反向失败同样存在：真正互不相关的发现不强行同树——parent 归属由问题性质决定（见 references/child-body.md）。

## 切分轴：实现责任，不是功能

children 沿实现结构切：每个实现 child 是系统结构模型里的一个责任单元（部件、边界或入口面），不是一项用户功能。责任单元取系统 C4 分解中的 container 或 component；repo 已有按 C4 组织的设计文档时直接沿用其元素，并以必读章节引用、不在 umbrella 复写；没有时按 `skill://software-design` 的层级规则在 umbrella「系统定位」中列出。入口面按实际的代码与部署单元划分，不按方向里点名的入口个数：两个入口共用一个实现单元就是一个 child，事实未明时写作期查清再分。一项功能通常横跨一个 owner 与多个消费面；按功能切，每个 child 会各自定义共享的类型、状态与错误分类，同改核心文件，共享结构由先合入者事实定义。功能结果进 umbrella「关闭验证」，由具名 child 承担端到端验收。

1. **找权威契约**：在 umbrella「系统定位」选定的模型上，列出本次新增或变更、且另一实现单元依赖的状态与规则——状态空间与领域类型、状态转移与生命周期锚点、schema、接口/协议语义、错误分类、所有权。每项恰有一个 owner：创建并维护它的部件。外部系统拥有的状态只写来源与本系统的适配部件，不把适配部件写成 owner。现有 owner 或状态写入方要靠代码事实确认时，写作期读代码确认；事实推翻候选 owner 就先修树根，再写实现 child。
2. **分核心与外围，按权威判定而非按名字**：核心 = 维护或改变某项权威契约的 owner 实现，以及本次变更的中心逻辑；外围 = 只消费已定契约的部分，如调用方迁移、不承担准入的入口面、文档对齐。承担唯一 parse 点的 handler、schema 生效前提的迁移、验收所需的观测属于核心依赖，不因名字排到最后。
3. **契约先定**：消费者 child 写出前，它依赖的契约已在树根裁决；写作中发现的缺口按 decision-closure 当场收口——取得事实，或与 subagent 讨论后裁决——不臆断，不登记成未决项，不留给 PR。
4. **owner 先落地**：契约的代码落地归 owner 的核心 child，同一 child 交付真实行为和一条经真实入口的最薄路径以供验收；不另立只有类型/接口、只能 typecheck 的基座 child。消费者 Depends on 它实际需要的 owner 后置条件，之后按物理共面编排并行。已有有效契约直接沿用，不补造阶段。
5. **契约只在 owner 处修订**：消费者发现契约不够用，走设计修正回到 owner 与树根，不在本地扩展或另立副本。

适用条件：至少一项新增或变更的状态/规则被多个实现单元依赖时启用 owner/消费切分；分散在无共享状态部件上的独立缺陷，按结构根因聚类（见 umbrella-body 系统定位）。任何 child 需要锁、对账、补偿或同步才能与 sibling 保持一致，说明 owner 归属或切分有误，回到第 1 步修正，不加机制。

## 内容分类

| 类别 | 处置 |
|---|---|
| 已知事实与约束 | 写来源；包括业务动机、架构不变量、锚点、已裁决目标级决策。已有权威文档承载的，按下文「权威文档只引用」写必读章节；树内新裁决的条款，children 逐字快照，不仅放指针。 |
| 跨实现单元契约 | 树根裁决并写明 owner；只钉协作所需的最小语义与确有必要的形状/标识。owner child 先落地，消费者快照其语义条款。 |
| 自由实现细节 | 单元内部命名、命令拼写、内部组织默认留实现者；不同选择既不改变操作员结果、也不迫使另一实现单元同步改变，就不预钉。验收命令本身仍须具体可执行。 |
| 写作期缺口 | 缺失事实与未定分叉不进正文：实现前可得的现在取得，设计分叉与 subagent 讨论后裁决；只有已定方案的运行结果可写成具名 child 的验收行。 |

不同选择会改变操作员观察结果的分叉属于目标级决策，会迫使另一实现单元同步改变的分叉属于契约级决策；二者都必须收口，不能一句「归 PR 定」下推。流程见 decision-closure。

**权威文档只引用。** 事实、架构、契约或约束已由权威文档承载时——repo 内版本化的设计文档、规范、ADR、README，或外部标准与官方文档——issue 不复写、不摘抄，留「必读章节」：文档路径或链接 + 章节标题锚点 + 一句说明它决定本 issue 的哪部分。复写出的副本会与源头漂移，执行者分不清哪份算数。issue 只写文档里没有的：本树新裁决、相对文档的差异与本次要改的部分。本树裁决会改变权威文档时，由 owner child 在同一 PR 更新该文档，issue 写要改的语义而不是整段新文；文档更新合入后，活跃 issue 里对应的快照换成必读章节。没有权威文档的新契约以树根为源，children 照常逐字快照。

| 当前工作 | 必读 |

| 写或改 child；定核心/外围责任；选 audit/收尾类型 | [child-body.md](references/child-body.md) |
| 补齐决策、架构切片、log 义务或设计修正 thread | [comment-layers.md](references/comment-layers.md) |
| 写作中发现遗漏或未知；全文有「归 PR 定 / 待定 / 再说」或目标级、契约级分叉 | [decision-closure.md](references/decision-closure.md) |
| 树完成后的对抗审查；用户要求重验 | [adversarial-review.md](references/adversarial-review.md) |
| 发布、挂接、re-parent、label | [mechanics.md](references/mechanics.md) |

只在相应工作不发生时跳过该文档；发布前自检总要过。除用户明确只要草稿外，完整 body + comment 层和对抗审查属于交付，不能把它们隐式留给下个会话。

## 完成方式

- 写不出的区块是写作期缺口：当场调查或裁决补齐，不以空话填充，也不登记成未决项。目标完备靠性质、外部契约、跨单元契约与目标级裁决，不靠穷举实现。
- 对抗审查每轮换面，查实怀疑并记录反证；连续一轮无新发现才结束，零发现也记录。
- 操作员修正衡量尺时，先实证检查新解释，指出哪些旧产出复读了旧误解，再重扫全部产出；报告区分新发现、修正和重验通过。
- 维护本方法时，用非本方法生成的真实工件做生成性基准，逐区块及 child/comment 层检查方法能否引出它；不拿自己的产出循环确认。具体方法在 adversarial-review。
