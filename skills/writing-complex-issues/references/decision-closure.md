# 决策收口

什么时候读我：写作中发现任何遗漏、分叉或未知时；树上存在「归 PR 定」「形态待定」「报错还是告警再说」「二选一并落地」类留白时。把方案分叉原样写进「预期结果」发布（「方案 A 或 B，选哪个待定」）也是留白——它把本该在树上完成的裁决转嫁给实现者。

## 发布不变量

发布的树里不存在未决项或等待结论的阻塞项：目标、owner、跨实现单元契约、责任边界、范围与 child 集合都在写作期闭合。唯一可以后置的是**已定方案的运行结果证据**，而且只能后置到某个具名 child 的验收行或继承验证义务。审查时问：实现者是否仍需替作者选择目标、owner、契约或任务范围？是，就是未收口。

写作中发现遗漏就当场收口，不登记成未决问题、不开调查 issue gate 后续实现、不写「方向未提供，按 X 假设推进」等待日后修正。

## 三分类详则

| 类 | 定义 | 处置与理由 |
|---|---|---|
| a：已知事实与约束 | 业务动机、架构不变量、代码锚点、必须保持/不许残留的性质、已裁决的目标级决策、已裁决的跨实现单元契约（owner、状态空间、不变量、错误分类、接口语义） | 写，且自包含——树内新裁决的契约条款逐字快照进来。指针的代价：headless 读者被迫做跨 issue 图遍历，每一跳都是偏离点。已由权威文档承载的写必读章节，不复写（SKILL.md「权威文档只引用」）：文档在 checkout 里可直接读，复写的副本反而漂移 |
| b：本质自由的实现细节 | key 命名、命令拼写、单元内部结构与模块划分、契约之外的签名拼写 | 默认不写。写出来就成虚假约束——headless agent 会把它当真理，更优的实现被预先封死。想写时先试着用判据升格为 a 类；升不了格就是预言 |
| c：写作期缺口 | 写作中发现的缺失事实或未定分叉：第三方行为、跨组件可行性、现有 owner 或写入方、性能 | 写作期工作项，不是发布类别：按下方收口流程转成 a，或确认属于 b。把猜测包装成 spec 与把缺口留给实现者一样不可接受 |

a/b 判据有两条，任一成立即为 a：**这个分叉的不同选择会不会改变操作员观察到的结果**（目标级）；**会不会迫使另一实现单元同步改变它的输入、输出、状态解释、错误处理或责任边界**（契约级）。都不会 → 自由细节（b）。第二条按实现单元判定，与 child 怎么切无关：把两个消费者并进一个 child 不能让契约消失。契约级只钉协作所需的最小语义与确有必要的形状/标识，owner 内部组织、算法、私有命名仍是 b。a/b 误判是最大偏离源——最常见的两种形态是把目标级决策（停机语义、错误分级政策）误标成「实现细节归 PR」，和把跨单元契约（共享状态的 owner、状态空间、错误分类）留给各 child 的 PR 各自定义。

## 收口流程

1. **扫全树收集**所有留白与写作中发现的缺口，逐个过三分类。
2. **按缺口来源处置**：
   - **实现前可得的事实**（代码现状、现有 owner、第三方文档、可在草稿环境或经既有凭据在目标环境跑通的实验）→ 现在取得：派 subagent 读代码、跑实验、查文档，带证据写成 a 类。一个「某机制其实是死代码」的发现可以把决策从「变更行为」简化为「定义行为」。
   - **设计分叉**（a 类判据成立）→ 与 subagent 讨论后由作者当场裁决：给它事实、约束、候选方案与作者初判，通常同时取保守（压测风险、找更省事方案）与发散（重构问题、找实质不同方案）两个视角；逐条查实异议，再裁决。事实唯一指向某方案或属于 b 类时不机械讨论。
   - **只能在实现后观察的结果**（已定方案的吞吐、真实负载下的延迟等）→ 优先选正确性不依赖它的方案；它是已定方案的结果性质时，写成 owner child 经最薄真实入口的 assumption 验收行，使其在 owner PR 就暴露。不预写「失败则改用方案 B」——那是换个位置的二选一；失败时走 comment-layers 的设计修正。若每个候选方案的成立都取决于这类事实，先在写作期用最薄原型或草稿环境实验取得；目标环境确不可达、原型也复现不了时，向操作员说明缺哪项事实与已试途径，取得前不发布依赖它的 issue——缺口留在写作会话，不进 GitHub。
   - **操作员独有事实**（业务动机、商业约束、授权范围）→ 先查请求、历史与项目证据，足以支撑就引用；仍缺且会实质改变目标、范围或授权时，写作期直接问操作员并等答复。不用 subagent 讨论产生它，也不虚构；未提供的预算、偏好不构成缺口。追溯不到方向、契约或 repo 既有承诺的**进口目标**不立 child，也不为它提问。
   - **外部 owner 的状态**（别的 repo、第三方、IaC 等不归本系统维护的对象）→ 本系统无权裁决：写作期向源头请求并等待结论。源头已承诺交付时，作为外部 Depends 边写明所需的已交付后置条件；本树契约只写本系统的适配部件。
3. **全局求解**：全部缺口 + 全部约束（契约、既有裁决、历史教训、升级现实、运维路径）一起解——决策相互耦合（受控通道与直接 API 的区分、同一把错误分级尺），逐个独立拍会拍出矛盾。结论直接进 umbrella master record，不另留过程存档。
4. **回填**：umbrella 发 master record（决策表：裁决、依据、被否方案及否决理由 + 交叉自洽检查），活跃 body 的留白替换为结论，每个受影响 child 发决策 comment。
5. **范围性质化**：裁决时把机制枚举改写成性质（「一切 X 路径都经 Y」），再明确实际保证机制、覆盖边界与真实验证路径。遵循全局 functional/ADT 偏好；语言与项目模型支持时优先用领域类型、受限构造和编译器穷尽检查，否则按项目惯例使用边界解析、运行时校验或协议约束。不预钉品牌类型或特定 union，不声称性质措辞或 typecheck 能自动覆盖所有运行时旁路；验收仍须直接观察目标结果。

依赖边只指向**已交付行为的后置条件**（owner 落地的契约、上游已交付的能力），不指向某个 issue 将产出的事实或结论——后者是换了形态的未决项。
