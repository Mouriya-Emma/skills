# writing-pr

PR 承载实现说明与证明：正文说明 diff 怎样兑现 issue 的原因、结果与契约；证明按 issue 的影响范围分层，落在实现说明与 `ghc ev` 记录上。现场、原因、范围和预期结果在 `writing-issue` skill，裁决在 `review-pr` skill。讨论位置与已合并记录的处理按 `git` 规则的「GitHub issue / PR routing rule」，更严的 repo-local 流程优先。

模板由 PR 交付的 issue 决定：「无代码变更」issue 用无代码变更模板，其余用标准模板并按影响范围取证明形式；把树的缓冲分支合入默认分支的用 tree PR 模板。总体验收 issue 没有自己的 PR，证据发在它上面，由 tree PR 关闭。

## 身份

- 一个 PR 交付一个 issue，正文第一行 `Closes #<N>` 或 `Closes <owner>/<repo>#<N>`。
- base 由 issue 的位置决定，`ghc lint <PR>` 检查：独立 issue 合入默认分支；树内 child 合入缓冲分支 `tree/<树根 owner>-<树根 repo>-<树根编号>`，到 tree PR 合并时才关闭。每个 issue 有自己的分支和 HEAD，PR 的 diff 只含本 issue 的改动。
- 标题和正文用中文；代码、路径、命令与工具输出原样。conventional-commit 前缀仅在 repo 已有惯例时用。
- 只修改尚未通过 review 的 open PR。每个 PR 只有一轮只读审查，结论对当前 patch 生效：无冲突 rebase 让 HEAD 变化而 patch 不变时结论仍然有效；改动本 PR 的 hunk 或追加提交会改变 patch，之前的结论失效，需要再次审查。review 通过前如需重试，续用原 branch 和 PR：同步更新实现说明，需要证据包时按 `ghc ev check` 列出的过期项在新 patch 上重新采集并发布，再发重试评论。通过后 PR 只经 `ghc land` 落盘，落盘途中 patch 变化同样要复核。合入之后再出现什么问题必须开新的 issue 和 PR。

## 实现说明（标准 PR）

回答「这个 diff 为什么能解决 issue 写明的原因」。只写实际相关的项，不复制 issue 的 Why，不逐文件复述 diff：

- **不变边界**：改动只作用于部分人群、入口或状态时，写哪些不受影响，靠哪个符号、分支条件或类型把它们挡在改动之外；对应 `[保持]` 结果时注明编号。
- **机制**：改在哪个责任单元、用了什么机制、它怎样消除原因而非只压住症状；关键实现附文件 + 符号。
- **测试**：可测试面的每条结果写明证明它的测试文件与用例名。这些测试随本 PR 提交，经真实入口或真实本地依赖运行；证明 `[改]`、`[新]`、`[删]` 的测试去掉本次改动即失败，`[保持]` 由覆盖该路径的测试守着。
- **契约**：维护或改变的契约落在哪个符号；消费的契约如何使用、没有在本地扩展或重定义。
- **切换**：同步迁移的调用方、删除的旧路径与兜底；未迁移的写原因与承接 issue。
- **阅读入口**：diff 同时含中心逻辑与机械改动时，指出核心改动在哪。
- **实现选择与偏离**：issue 留给实现者的选择写所选方案与理由；比较过两个及以上方案时用 issue 决策表的四列（分叉、裁决、依据、被否方案及否决理由）。会改变操作员结果或跨单元契约的偏离不能在 PR 自行放行：在 PR thread 提出，由 issue 裁决后再实现。
- **未验证与风险**：没覆盖的路径、推断而未观察的行为，明确标为未验证。

## 证据（标准 PR）

证明挂在 issue 的预期结果上：每条结果都要有证明，让 reviewer 不读代码也能看出这条结果达到了。issue 不规定怎样验证；从哪个入口观察、用什么输入、读哪个数，由你在实现完成后决定。`ghc ev plan <issue>` 列出每条结果可用的模板与步骤。

**证明分层，按结果实际经哪个面观察判定。** 面分成可测试面 `library`、`cli`、`service`、`data` 与外部面 `gui`、`iac`、`agent-config`：

- **可测试面**：PR 上名为 `test` 的检查为 success 时，每条结果由随本 PR 提交的行为或集成测试证明。测试必须驱动真实入口或真实本地依赖，`[改]`、`[新]`、`[删]` 的测试去掉本次改动即失败，`[保持]` 由覆盖该路径的测试守着；`## 实现说明` 写明每条结果对应的测试文件与用例名。issue 的影响范围只含可测试面时，这个 PR 不再采集或发布证据包。
- **外部面**：每个面至少有一条结果经 `ghc ev` 记录证明。`ghc ev plan` 按面列出步骤：`gui` 交真实会话的截图，`iac` 交 preview → apply → readback（按此顺序），`agent-config` 交加载本分支配置的会话。同时含可测试面时，其余结果由 `test` 证明。
- **回退**：仓库还没有 `test` 检查时，全部结果都用 `ghc ev` 记录证明；不能既没有 `test` 也没有记录。
- **总体验收 issue**：它的结果始终用 `ghc ev` 记录证明，按面交步骤；child 的测试和记录都代替不了组合后的验收。

**模板由结果类型决定。** issue 在每条结果上标了类型作参考，`ghc ev plan` 把它显示成对应模板；采集时按实际类型用 `--kind` 指定，证据包标出差异，不为此改 issue。改动前的现场就是 issue 的「## 现场」，采集只在实现后的检出上进行。下表写 `ghc ev` 记录交什么；由 `test` 证明的结果把同一形态写成行为测试，并在实现说明里写明文件与用例名：

| 类型 | 交什么 |
|---|---|
| `[改]` | 改动后经原入口的观察，与该结果在「现场」里的那一幕对照：同一个入口、同一个输入，现在读到什么 |
| `[新]` | 经新入口观察到新能力的表现；issue 逐个写了 variant 的，每个 variant 都要观察到 |
| `[删]` | 经原来的入口观察到它已经不在：原入口的拒绝或缺席，以及 issue「不应残留」列的东西查不到 |
| `[保持]` | 经被改的代码路径观察到它保持原样，读数与「现场」一致 |

实际情况与 issue 标的类型不同（标 `[改]` 的其实是全新入口）时，采集用 `--kind` 按实际类型。

**每条记录写看点。** `--shows` 用一句话写明 reviewer 能从这条证据里看出什么：读哪一行、哪个区域、哪个数字，它说明结果的哪一部分。写具体的读数（「第 3 行 `status: rejected`，exit 2」「列表里不再有『旧开关』一项」），不写结论（「功能正常」）。看点说的东西在记录里找不到，这条证据不成立。由 `test` 证明的结果没有记录，它的看点就是实现说明里的测试文件与用例名。

**记录的形式由面决定。** 结果出现在界面上时交渲染后的画面：终端界面（TUI）的原始终端字节读不出画面，在会话里截图，用 `--artifacts <目录>` 随记录登记。

采集：

1. 开工前跑 `ghc ev plan <issue>`，逐条结果定下：需要 `ghc ev` 证明的，从哪个真实入口观察、在哪个环境、需要哪些前置（部署目标、依赖服务、数据、凭据），实现要把这个入口交出来；由 `test` 证明的，定下由哪个测试经哪个入口驱动。
2. 实现、提交、`test` 通过之后，采集需要 `ghc ev` 的结果：
   - 命令行能读到的：`ghc ev run <issue> --result N [--step S] --shows "<看点>" -- <命令>`。一条记录同时证明多条结果时用 `--result N,M`。
   - 界面上的：Web 界面按 `ego-browser` skill、Tern 界面按 `tern` skill 操作到该状态并截图，再 `ghc ev attach <issue> --result N [--step S] --shows "<看点>" <图片>`。
   - issue 声明了多个面时用 `--face` 指明这条记录经哪个面观察；每个需要记录的面至少有一条结果经它观察。
3. 需要证据包时，`ghc ev check <issue>` 退出码 0 才开 PR；它列出的缺失、过期、无效项就是待办。工作区有未提交改动时 `ghc` 拒绝采集。记录按 patch 判定：HEAD 变了而 patch 不变（无冲突 rebase 追平 base）时记录照常有效；patch 变了才在新 patch 上重采。

**证据成立的两条规则。**

- 经真实入口观察：产品的 CLI、HTTP 接口、界面、控制面或数据库读回，环境按 issue 的「测试形态」，不升级；运行强度按 `runtime-verification-required` 规则。
- 记录只能经 `ghc ev` 产生：一次性的取证脚本、mock、stub 与 driver 的输出不写进记录；随 PR 提交、由 `test` 检查运行的行为测试是另一条证明路径。mock、stub、只固定内部实现或复制实现的测试，以及去掉本次改动仍然通过的测试，都不能证明可测试面的结果。

准备动作（造数据、起依赖、切换设置）和多条命令可以在同一条记录里，只要看点指向的读数来自真实入口。输出不手写、不挪用别次的；PR 正文不贴日志或截图。

**`test` 检查与证据包的边界。** 构建与 lint 说明不了任何一条结果达到了，不进证据包：它们是 PR 的 checks，`ghc merge-ready` 要求全部通过。名为 `test` 的检查对可测试面是证明，对外部面不是，外部面照常交 `ghc ev` 记录。仓库没有 `test` 检查时，按回退采集全部结果，并在送审的 HEAD 上跑一次构建、lint 与测试，把命令与结果作为 PR comment 发出。

**观察不到时。** 先分清是观察方式的问题还是结果本身的问题：

- 换一个入口、输入或环境能观察到：直接换，这是你的决定，不改 issue。
- 结果本身与事实不符（现场写错了，或它要求的行为与实现后的事实、既有行为矛盾），或它在本 issue 这一层没有入口：不改写结果迁就实现。在 PR thread（PR 还没开时在 issue 上）写「结果 N：<不符的事实与证据>；建议改为 <…>」或「建议移给 <能观察它的 issue>」，交派工方裁决；该结果的证据如实缺失，其余结果照常采集。issue 改写这条结果后只需重采这一条。
- 外部 blocker 用 `writing-issue` skill 发布并写解除条件。缺凭据先按 `credentials-from-owning-source` 规则查拥有方的 secret store 与本机既有来源。

证明只做一次：review 判断实现说明与证据而不重跑，`ghc land` 与合入后也不重跑。

## 模板

### 标准 PR

```markdown
Closes <owner>/<repo>#<N>

## 摘要

<1–3 句改动结果。>

## 实现说明

<不变边界、机制、测试文件与用例名、契约、切换、阅读入口、实现选择与偏离、未验证与风险中实际相关的项。>
```

正文不写证据、日志、截图或仓库检查段，`ghc lint <PR>` 把这类段落报为错误。

### 无代码变更 PR

每段用无序列表，一个 bullet 概括一个要点：写思路与语义变化（新增了哪条规则、收窄了哪个边界、删掉了什么及原因），不按文件或行复述 diff，不贴改前改后原文。兑现某条预期结果的要点末尾标 `（结果 N）`，每条结果都要有。diff 只能改 issue「范围」里列出的文件。

```markdown
Closes <owner>/<repo>#<N>

## 摘要

<1–3 句：这次文档更新解决 issue 的什么问题。>

## 做了什么

- <哪份文档的哪部分语义变了，同步核对了哪些关联文档>（结果 1）

## 调整思路

- <原有内容的问题或矛盾、依据、取舍与被否方案>

## 增加

- <新增的规则、概念、流程或章节要点>

## 减少

- <删除或收窄的内容及原因；无则写「无」>
```

### tree PR

树的 child 全部合入缓冲分支、总体验收 issue 的证据包齐全后，在每个涉及的 repo 开一个：head 是缓冲分支，base 是默认分支。它没有自己的实现说明与证据包。合并前提是 `ghc merge-ready <树根> --tree`。

```markdown
Tree <owner>/<repo>#<树根>

## 摘要

<1–3 句：这棵树交付了什么。>

## 关闭

Closes <owner>/<repo>#<N>（<合入缓冲分支的 PR 链接>）
Closes <owner>/<repo>#<总体验收 issue>（证据包 <链接>）
Closes <owner>/<repo>#<树根>
```

逐行 `Closes` 该 repo 里全部未关闭的树内 issue，树根所在 repo 的那个还关闭树根。落盘用 `ghc land <树根> --tree`：它先落树根之外的 repo，最后落树根所在 repo，并读回树内 issue 全部关闭。

### 重试评论（标准 PR）

```markdown
## 重试意图

本次重试处理 <review comment URL>，续用 <issue 链接> 的现有 branch / PR。
计划动作：<收窄的改动、契约更正，或换用的观察方式与类型>

## 实现变化

<本次重试改变了哪些不变边界、机制、契约或切换，正文已同步；未改实现则写「无」。>

## 证据

<需要证据包时写：HEAD <sha> 的证据包 <ghc ev publish 输出的 comment 链接>。>
```

没有证据包时删去「证据」一节，证明写在实现说明的测试文件与用例名里。无代码变更 PR 的重试评论写「重试意图」，再按「做了什么 / 调整思路 / 增加 / 减少」概括本次变化。

## 创建与发布

```bash
ghc ev check <issue>        # 需要证据包时：退出码 0 才继续
git push -u origin <branch>
gh pr create --repo <owner>/<repo> --title "<中文标题>" --body-file <body-file>
ghc lint <PR>               # 身份、分支与模板；无代码变更另查范围、链接与结果标注
ghc ev publish <PR>         # 需要证据包时发布；无代码变更 PR 也发布检查结果
```

`ghc lint` 与需要时的 `ghc ev publish` 退出码都是 0 才算发布完成；全部结果由 `test` 证明的 PR 跑 `ghc ev publish` 只报告无需证据包。`ghc lint` 非零时用 `gh pr edit --body-file` 修正后重跑；`ghc ev publish` 非零时按输出补采后重发，它发现疑似凭据会拒绝发布，换成不打印凭据的命令重采。再核对程序判断不了的：diff 单一连贯；实现说明与当前 HEAD 一致、对得上 issue 写明的原因，可测试面的每条结果都有测试文件与用例名；观察、推断与未验证项分开写；阻塞如实说明。落盘用 `ghc land <PR> --issue <issue>`。
