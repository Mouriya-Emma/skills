# writing-issue

本 skill 管单个 issue。两个及以上相关 issue 用 `writing-complex-issues` skill 组织成树；PR 的实现说明与证据用 `writing-pr` skill，关闭裁决用 `review-pr` skill。issue 与 PR 各承载什么按 `git` 规则的「GitHub issue / PR routing rule」，更严的 repo-local 规则优先；目标 repo 使用 coder-loop preset 时，先读 `presets/<preset>/contract.md` 的分类 label、必需段和 review replay 契约。

## 先写现场

issue 是一段叙事：已经发生了一件事，所以要改。写别的段落之前，先把这件事调查清楚，写成「现场」；目标、原因和预期结果都从现场推出。调查的对象是现在发生了什么，不是以后怎么实现。

现场回答「提出这条 issue 时已经发生了什么」，按 issue 的性质写：

| 性质 | 现场写什么 |
|---|---|
| bug | 谁在哪个入口做了什么，看到了什么，本该看到什么；从什么时候开始，是否每次出现，影响到谁 |
| 新功能 | 这件事现在是怎么做的，或者哪一次想做而做不到：一次具体的经过，谁在什么场合需要它，没有它付出了什么 |
| 重构 | 哪几次具体的改动、排查或事故暴露了痛点，当时多付出了什么；现在的结构是什么样 |
| 删除 | 要删的东西现在在哪里，谁还在用或已经没人用的依据，留着它造成了什么 |

- **亲自取到现场。** 写作者自己复现、运行、打开界面或读日志，把看到的东西原样放进来：命令与输出、日志片段、截图、原文引用与链接，并写明基准提交 `owner/repo@<sha>` 和环境。读代码推演出来的「会发生什么」不是现场：代码审计的发现先复现成一次真实的经过，复现不出来就不为它写 issue。
- **写经过，不写评价。** 「体验不好」「不够健壮」「需要优化」不是现场；写哪一次、做了什么、结果是什么、多花了多少。
- **对象写具体。** workload、样本总体、使用场景、涉及的数据量写出实际的那一个，不以「真实 / 代表性 X」代替，也不把定义责任推给实现者。
- **现场里没有改法。** 改法在决策表或 PR；现场混入改法，后面的目标和结果都会被它牵着走。
- **写不出来就停。** 缺的事实现在取得：复现、读日志、查历史 issue 与 PR，或按 [decision-closure](../writing-complex-issues/references/decision-closure.md) 派 subagent 取得；只有操作员知道的经过直接问操作员，写成陈述并注明出自操作员，不贴对话原话。现场仍然空着时，这条 issue 还不能写。

读取已有 issue/PR 先用 `gh-contract` skill（`../gh-contract/SKILL.md`）的 `ghc fetch <ref>` 完整落盘，之后只读本地文件。转述标清来源，来源互相矛盾时点明。

## 从现场往后推

后面每一段都要能指回现场；指不回去的句子是写作者自己加的，删掉。

**一个问题。** 一段连贯的现场能撑起整个 issue；现场讲的是几件互不相干的事，就拆成树。正文不放草稿 ID、临时路径，也不写编排（谁实现、用哪个 agent 或模型、实现顺序、分支安排）：那由交付方决定（本机会话交付时按 `delivering-issues` skill）。agent、模型或交付流程本身是要改的对象时除外。

**目标。** 现场里的哪件事不再发生，或者变成什么：谁在哪里观察到什么。自包含，不贴请求原话。目标之外、现场没有提到的改进不自行添加。

**原因。** 现场为什么会发生：哪个责任单元的哪项状态或规则、哪条不变量或缺失的能力产生了它，附文件、符号和当前行为。原因在写作期查证并带证据，不开前置调查 issue，不把未证实的原因留给实现者；新功能写现有单元缺什么能力。原因不是改法：写「值在 Y 处未经 parse 跨域」，不写「在 Y 加校验函数」。

**责任定位。** 写明问题落在哪个现有责任单元，它维护相关状态（owner）还是只消费既定契约，哪些调用方受影响、是否同步迁移。状态的 owner 在别的单元、repo 或外部系统时，向 owner 提请求或依赖它，不在消费侧另立副本。

**必要决策。** 会改变操作员观察结果、或迫使另一实现单元同步改变的分叉（权威归属、状态空间、错误分类、接口语义），在 issue 裁决并写进决策表，只钉协作所需的最小语义；单元内部的组织、算法、命名留给 PR。树内 child 不自行裁决跨单元契约：用契约引用 `owner/repo#<树根> 决策 <comment-id> §K` 继承树根条款，缺失或冲突回到树根裁决。发布的 issue 不含未决项，写作中发现的未定分叉按 decision-closure 当场收口。

**预期结果。** 每条结果写现场里的哪一幕之后变成什么样，并标一个类型：

| 类型 | 含义 |
|---|---|
| `[改]` | 现场里已有的行为变成另一种：修 bug、调整行为、重构后同一入口的表现 |
| `[新]` | 现场里做不到的事之后能做 |
| `[删]` | 现场里存在的入口、行为或数据不再存在 |
| `[保持]` | 改动经过的路径上，现场里正常的行为保持原样 |

- 类型是给交付方的参考：它决定证据默认用前后对比、新功能还是删功能的模板（`writing-pr` skill「证据」）。采集证据的人发现实际情况不同时按实际类型采集，不为此改 issue。
- 改动只作用于部分人群、入口或状态时，单列一条 `[保持]` 写其余部分的已有行为不变。
- 裁决了状态空间或错误分类时，逐个 variant 写可观察表现（哪个错误码对应什么界面、消息或 exit status），不用「出错时给出提示」概括。
- 结果要能被证伪：读者能说出看到什么算没达到。发布前设想最省事的交付：用户的问题没解决也能说每条结果都达到了，就把结果写得更具体。
- **不写怎样验证。** issue 写成时实现还不存在，写作者不知道实现后从哪个入口、用什么输入、读到什么字面值。这些由采集证据的人在实现后决定并写进证据，issue 里不出现命令、输入脚本、期望的字面读数或指派给某人的验证步骤。
- 上游移交过来、要在本 issue 的环境里观察的结果，写成本 issue 的一条结果并注明「承接 `owner/repo#K` 结果 N」，不可再次移交。

只改给人读的文本（README、设计文档、指南、ADR）用「无代码变更 issue」模板。skill、prompt、rule、agent 定义由 agent 读取，按标准模板写，面是 `agent-config`。

## 影响范围与测试形态

`## 影响范围` 每行一个面：`gui`、`cli`、`service`、`library`、`data`、`iac`、`agent-config`。面决定证据以什么形式交（例如 `gui` 交真实会话的截图），由 `ghc ev plan` 列出。`library` 没有自己的入口，经消费它的真实入口观察。跨族组合（应用、基础设施、agent 配置）应拆分；确需在同一 repo 一起交付时加一行 `打包理由：…`。跨 repo 必须拆分。

`## 测试形态` 写一个值，说明证据在多真实的环境里采集：

- `e2e`：真实入口加真实目标环境，部署后观察。不在 issue 树里的 issue 只能是它。
- `集成`：真实入口或公开接口，依赖是真实的进程、数据库、文件，在本地或测试环境（`iac` 是测试环境上的 apply，`agent-config` 是加载本分支配置的本地会话）。
- `最薄入口`：owner 经最薄的真实入口观察它维护的状态语义。不适用于 `gui`、`iac`、`agent-config`。

树内 child 只用后两种，它的 PR 证据证明这一个责任单元，不做 e2e。树的 e2e 是单独的总体验收 issue：全部 child 合入缓冲分支后，按用户功能逐项在组合后的系统上验收，不按 child 或 PR 逐个验。

## 模板

正文中文、简练；代码标识符、路径、API、label、`Depends on` / `Blocks` / `RFC:` 保留英文，源引文和工具输出保持原样。

### 标准 issue

```markdown
# <中文标题：一个问题>

## 现场

<提出这条 issue 时已经发生的事：经过，原样记录（输出、日志、截图、引文与链接），基准提交与环境，出现的频率和影响到谁。不写改法。>

## 目标

<现场里的哪件事不再发生，或变成什么：谁在哪里观察到什么。>

## 上下文

- **Repo**: `owner/repo` <代码与 PR 所在的 repo；issue 开在别的 repo 时也写代码所在的这个，`ghc` 在它的缓冲分支里找 child 的 PR>
- **Design doc / source**: <设计文档路径或 issue/PR 链接；没有时省略>
- **Conventions**: <跨 repo 时明确遵从哪一份契约>
- **Anchors**: <文件 + 符号 + 当前行为；实施前在当前 HEAD 核对>

## 原因

<现场为什么会发生：责任单元的哪项状态、规则、不变量或缺失的能力，及写作期查证的证据。不写改法。>

## 责任与必要决策

- **责任单元**: <现有单元；owner 或消费者>
- **受影响方**: <调用方/消费者及是否同步迁移>
- **决策**: <无则写「无」；有则写成下表，一个分叉一行>

| 分叉 | 裁决 | 依据 | 被否方案及否决理由 |
|---|---|---|---|
| <会改变操作员结果或迫使另一单元同步改变的选择> | <采用的方案> | <代码现状、既有惯例、操作员给出的事实或契约引用> | <方案：否决理由> |

## 预期结果

- 结果 1 [改]：<现场里的哪个行为变成什么；裁决了状态空间时逐 variant 写表现。>
- 结果 2 [新]：<现场里做不到、之后能观察到的能力。没有时删去。>
- 结果 3 [删]：<不再存在的入口、行为或数据。没有时删去。>
- 结果 4 [保持]：<改动经过的路径上保持原样的行为。没有时删去。>

## 范围边界

- **不应残留**: <本次确有的旧路径、兜底、字面量>
- **不在范围**: <邻近但不做的项及其归属>

## 约束

<可选；源强加的外部约束，或树内继承的契约引用。>

## 影响范围

- <面，可多选>

## 测试形态

<e2e / 集成 / 最薄入口，一个值>

## 依赖关系

- Depends on: <issue 链接>（<需要的上游已交付后置条件>）
- Blocks: <issue 链接>（<谁需要本结果>）
```

树内 child 的扩展区块和总体验收 issue 的模板见 [child-body.md](../writing-complex-issues/references/child-body.md)。

### 无代码变更 issue

issue 列出要改的确切文件，PR 的 diff 不得超出这份清单（`ghc lint <PR>` 检查）；要多改文件先改「范围」。结果不标类型，不采集运行证据。

```markdown
# <中文标题：一个问题>

类型：无代码变更

## 现场

<现有文档哪里错了、过时了、互相矛盾或缺了：引用原文与位置；读者因此做错或做不了什么。>

## 目标

<读者读完文档后能做出什么正确判断或操作。>

## 范围

- <要改或新建的文件，repo 内的确切路径，一行一个>

## 预期结果

- 结果 1：<改完后文档明确陈述的一条语义>

## 范围边界

- <不改的部分及其归属>
```

### retroactive umbrella

组织已落地工作的追溯性 issue 属于树，用 [umbrella-body.md](../writing-complex-issues/references/umbrella-body.md) 的 retroactive 模板；它记录已落地事实，不回写已落地的 issue/PR。

## 归属、发布与修订

1. **home repo**：要改的对象由哪个 repo 声明，issue 就开在哪个 repo。app 的部署归 km 还是 IaC，按 `personal-infra-routing` 规则的归属判据定。
2. **parent**：先定 parent 再建 child；一个 child 只有一个 issue parent，另一条线用散文引用；跨 repo（同 org）可以连接。API 操作与失败恢复见 [sub-issue-api.md](references/sub-issue-api.md)。PR 只用 closing keyword 连接 issue。
3. **发布后**跑 `ghc lint <issue>`，非零就修正正文后重跑。lint 判断不了的自己核对：现场是写作者取到的经过，不是推演或评价；目标、原因和每条结果都能指回现场；原因有证据链；没有未决项或指向未来结论的依赖；不变边界与逐 variant 结果齐全；每条结果能被证伪；正文里没有验证方法、命令或指派给人的步骤。
4. **修订**活跃 issue 时，错误引用、作废前提和过时内容直接替换；裁决、范围变化另发 comment 留记录（[comment-layers.md](../writing-complex-issues/references/comment-layers.md)）；树内同时核对契约引用仍指向有效条款。改写一条结果的文字会让它已采集的证据过期，其余结果的证据不受影响。已落地的记录不回写。
