# writing-complex-issues

交付的是能在 headless 环境仅凭完整 issue thread 执行的任务树：树根和每个 child 都从现场写起（提出它时已经发生了什么），目标、契约和结果由现场推出；跨实现单元的权威契约在树根先定，child 内部实现细节不预钉；树里没有未决问题，写作中发现的遗漏当场收口。

单个 issue 的写法（现场、原因、带类型的结果、模板）继承 `writing-issue` skill；图边、讨论位置与已落地记录按 `git` 规则的「GitHub issue / PR routing rule」。

## 成树判据

同一方向或同一次调查产出两个及以上相关 issue 就是树：先写树根再写 children。契约、决策、共享根因、依赖图只在树根有位置，平铺发布后无处回填，跨 issue 的「二选一」会原样转嫁给实现者。树有两个入口：自顶向下（方向拆成 children）和自底向上（审计、调查先产出发现，再由 umbrella 或充当树根的 audit 组织，见 [child-body.md](references/child-body.md)）。真正互不相关的发现不强行同树：parent 由问题性质决定，不按发现途径、repo 或批次分组。

## 开树前：解析操作员方向

| 输入 | 落位 | 尚未确定时 |
|---|---|---|
| 现场 | 方向背后已经发生的事：哪几次经过让操作员提出这个方向。写作期取到原样记录（输出、日志、截图、引文与链接），写进树根的「现场」 | 查 repo、历史 issue 与 PR、日志并自己复现；只有操作员知道的经过直接问操作员。现场取不到时不开树 |
| 指称对象（我们的 API/CLI/系统） | 具体 repo、环境与版本锚；umbrella 说明认定依据 | 派 subagent 查 repo、部署与已有上下文，带证据落位；仍无法确定时直接问操作员。不编路径，不留 unknown |
| 目标 | 自包含的结果陈述：谁在哪里观察到什么；方向里决定目标的对象、数值与限定词转写进目标、范围或约束，不贴操作员原话 | 方向读不出结果，或有会改变范围的不同读法时，先查已有上下文，仍无法确定就问操作员并等答复 |
| 业务动机 | 有来源的 Why，不用目标复读充当动机 | 操作员独有、缺失且会改变目标或范围的事实，问操作员并等答复 |
| 交付约束 | 截止期转绝对日期、预算入契约；children 以契约引用继承 | 没给就不虚构 |

高风险的第三方或跨环境假设在写作期验证，不开 gate 实现的验证 issue。

## 切分轴：实现责任，不是功能

每个实现 child 是系统结构模型里的一个责任单元（C4 的 container 或 component：部件、边界或入口面），不是一项用户功能。repo 已有按 C4 组织的设计文档时沿用其元素并以必读章节引用；没有时按 `ssot` skill 的层级规则在 umbrella「系统定位」中列出。两个入口共用一个实现单元就是一个 child。按功能切，每个 child 会各自定义共享的类型、状态与错误分类，共享结构由先合入者事实定义；功能结果写进总体验收 issue。

1. **找权威契约。** 列出本次新增或变更、且另一实现单元依赖的状态与规则：状态空间与领域类型、状态转移与生命周期锚点、schema、接口语义、错误分类、所有权。每项恰有一个 owner，即创建并维护它的部件；外部系统拥有的状态只写来源与本系统的适配部件。owner 靠读代码确认，事实推翻候选 owner 就先改树根。
2. **分核心与外围。** 核心是维护或改变权威契约的 owner 实现，以及本次变更的中心逻辑；外围只消费已定契约（调用方迁移、不承担准入的入口面、文档对齐）。按权威判定，不按名字：承担唯一 parse 点的 handler、schema 生效前提的迁移属于核心。
3. **契约先定。** 消费者 child 写出前，它依赖的契约已在树根裁决；写作中发现的缺口按 [decision-closure.md](references/decision-closure.md) 当场收口，不留给 PR。
4. **owner 落地契约。** 契约的代码落地归 owner 的核心 child，同一 child 交付真实行为和一条经真实入口的最薄路径以供验收；不另立只有类型或接口、只能 typecheck 的基座 child。消费者 Depends on 它实际需要的 owner 后置条件。依赖要写全：交付方据此判断哪些 child 可以同时进行，一个 child 在它依赖的后置条件都已交付后开工。
5. **契约只在 owner 处修订。** 消费者发现契约不够用，走设计修正回到 owner 与树根，不在本地扩展或另立副本。

至少一项状态或规则被多个实现单元依赖时才启用 owner/消费切分；分散在无共享状态部件上的独立缺陷按结构根因聚类。任何 child 需要锁、对账、补偿或同步才能与 sibling 保持一致，说明 owner 归属或切分有误，回到第 1 步。

## 总体验收与测试形态

树的验收与单个 issue 不同：单个 issue 的 PR 自己做 e2e；树里 e2e 不面向任何一个 PR，而是单独一个**总体验收 issue**（`类型：总体验收`，模板见 [child-body.md](references/child-body.md)）面向功能做。全部实现 child 合入树的缓冲分支后，它按用户功能逐项在组合后的系统上做真实的端到端验收；每条结果是一项功能，不是某个 child 的复验。它不改代码、没有自己的 PR，由 tree PR 关闭；证据在缓冲分支的当前提交上采集，child 的证据不算数。

每个 child 在「测试形态」声明它的 PR 证据在哪里采集，只能是 `最薄入口` 或 `集成`：owner child 默认 `最薄入口`（面是 `gui`、`iac`、`agent-config` 时没有最薄入口，用 `集成`），外围 child 用 `集成`，只改给人读的文本的用无代码变更类型。每个实现 child 都要出现在总体验收某一条功能结果的「经由」里。这些结构由 `ghc lint <umbrella> --tree` 检查。

## 写什么，不写什么

| 类别 | 处置 |
|---|---|
| 已知事实与约束 | 写来源。权威文档已承载的写必读章节；树内新裁决的条款，children 用契约引用 `owner/repo#<树根> 决策 <comment-id> §K` 继承，不复写 |
| 跨实现单元契约 | 树根裁决并写明 owner，只钉协作所需的最小语义；owner child 落地，消费者以契约引用继承 |
| 自由实现细节 | 单元内部命名、命令拼写、内部组织留给实现者；不同选择既不改变操作员结果、也不迫使另一实现单元同步改变，就不预钉 |
| 怎样验证 | 不写。issue 只写现场和带类型的预期结果；从哪个入口、用什么输入观察、读到什么字面值，由采集证据的人在实现后决定（`writing-pr` skill「证据」） |
| 写作期缺口 | 不进正文：实现前可得的事实现在取得，设计分叉讨论后裁决；只有已定方案的运行结果可以留给具名 child 的一条预期结果 |
| 编排 | 不写。谁或哪个 agent、模型实现，实现顺序、并行、分支与 rebase 安排由交付方从依赖关系推出（本机会话交付时按 `delivering-issues` skill）；agent、模型或交付流程本身是要改的对象时除外 |

会改变操作员观察结果的分叉是目标级决策，会迫使另一实现单元同步改变的是契约级决策；两者都必须收口，不能一句「归 PR 定」下推。

**权威文档只引用。** 事实、架构、契约已由权威文档承载时（repo 内版本化的设计文档、规范、ADR、README，或外部标准与官方文档），issue 只留「必读章节」：路径或链接、章节标题锚点、它决定本 issue 的哪部分。复写的副本会与源头漂移。issue 只写文档里没有的：本树新裁决、相对文档的差异、本次要改的部分。本树裁决会改变权威文档时，由 owner child 在同一 PR 更新它；合入后，活跃 issue 里对应的契约引用换成必读章节。

## 完成

- 写不出的区块是写作期缺口：当场调查或裁决补齐，不用空话填充。
- 除用户明确只要草稿外，完整 body、comment 层和作者自审都在本会话做完。自审按 adversarial-review：发现直接改进 issue 正文，过程与落空的怀疑回报操作员，不写进 issue；连续一轮无新发现才结束。
- 操作员修正衡量尺时，先实证检查新解释，指出哪些旧产出复读了旧误解，再重扫全部产出。
